# 飞机大战 — 面向对象设计模式综合实验报告

## 1. 实验环境

- **操作系统**：Windows 11 Pro
- **JDK 版本**：17
- **IDE**：IntelliJ IDEA
- **构建/运行方式**：直接运行 `src/edu/hitsz/application/Main.java`，依赖 `lib/commons-lang3-3.8.1.jar`
- **UML 工具**：PlantUML（VS Code / IntelliJ 插件渲染）
- **游戏框架**：Java Swing（JFrame + JPanel + CardLayout 路由），定时器 40ms / tick（25 FPS）
- **持久化**：Java 对象序列化至 `data/record.dat`

## 2. 实验过程

### 2.1 UML 建模

根据面向对象设计原则，对整个游戏中所有飞行物体、飞机、子弹、道具的继承体系做了一次完整的梳理。核心基类是 `AbstractFlyingObject`，定义了所有飞行物体共有的属性（坐标、速度、图像、有效性标记）和行为（`forward()` 移动、`vanish()` 销毁、`crash()` 碰撞检测）。从它派生出三条分支：

- **AbstractAircraft**：飞机类层次，英雄机 + 七种敌机
- **BaseBullet**：子弹类层次，英雄子弹 + 敌机子弹
- **AbstractProp**：道具类层次，五种道具

另外飞机与子弹都实现了一组 Observer 接口（`BombObserver`、`FreezeObserver`），飞机还组合了 `ShootStrategy` 作为射击策略。各层之间的泛化、实现、关联、依赖关系全部梳理在下面的 PlantUML 类图中。

### 2.2 设计模式应用

#### 2.2.1 单例模式 (Singleton Pattern)

**1. 应用场景分析**

英雄机在整个游戏中应该只有一个实例。不管玩家是在打第一关还是重新开始新一局，屏幕上的英雄机从始至终就是那一架。如果每次开局都 new 一个新的 HeroAircraft，不仅浪费内存，更麻烦的是其他模块（碰撞检测、道具生效、鼠标控制器）都持有对"当前英雄机"的引用——如果这个引用变来变去，状态同步就是灾难。

最初也想过用全局静态变量粗暴解决，但 Java 里没有真正的"全局变量"。单例模式正好是标准答案：构造函数私有，全局只有一个访问点 `getInstance()`，谁调用都拿同一个对象。

具体实现上用了双重检查锁（DCL）。`instance` 字段标记 `volatile` 防止指令重排——没有这个关键字的话，另一个线程可能拿到一个构造了一半的英雄机。`resetForNewGame()` 方法则承担了"软重置"的职责：新一局开始时不销毁单例，只是把血量回满、位置归位、buff 清掉、射击策略恢复成直射。

还有一个精巧的设计是 Buff 版本号机制。英雄机同时持有 `currentBuffPriority` 和 `buffVersion` 两个状态，道具通过 `applyBuff(priority)` 申请生效——低优先级的会被拒绝，高优先级的会覆盖并产生一个新版本号。延迟恢复线程醒来时，会拿着旧版本号来调 `clearBuff(version)`，如果发现版本号已经变了（说明玩家在这期间又吃了新道具），线程就"默默死亡"不执行恢复。用版本号而不是简单的布尔标记来防并发，代码量很小但效果很稳。

**2. 设计模式结构图**

```
@startuml
' 单例模式 — 英雄机（Singleton Pattern）
skinparam classAttributeIconSize 0

class HeroAircraft <<Singleton>> {
    - {static volatile} instance: HeroAircraft
    - currentBuffPriority: int = 0
    - buffVersion: int = 0
    - HeroAircraft(locationX, locationY, speedX, speedY, hp)
    __
    + {static} getInstance(): HeroAircraft
    + resetForNewGame(): void
    + applyBuff(priority: int): int
    + clearBuff(version: int): void
    + {abstract} shoot(): List<BaseBullet>
    __ 说明 __
    双重检查锁（DCL）+ volatile
    确保多线程下唯一实例
    Buff 版本号防并发覆盖
}

note right of HeroAircraft
    <b>单例模式关键要素：</b>
    ① 构造函数 private（包外不可 new）
    ② 静态方法 getInstance() 为全局入口
    ③ DCL：第一次判空避免不必要加锁，
       第二次判空确保只 new 一次
    ④ volatile 禁止指令重排
    ⑤ resetForNewGame() 替代重建，
       一轮游戏 = 一次软重置
end note
@enduml
```

#### 2.2.2 简单工厂模式 (Simple Factory Pattern)

**1. 应用场景分析**

游戏里有五种道具——回血、炸弹、火力、超级火力、冰冻。敌机被击毁时，按概率决定掉哪种道具，但敌机类不应该知道怎么"造"道具。如果让每个 Enemy 子类自己去 `new BloodProp()`、`new BombProp()`，那道具类的构造函数签名一旦变了，所有敌机类都得跟着改。

`PropFactory` 用了一个静态方法 `createProp(type, x, y)`，参数只传一个类型字符串和坐标。敌机调用的时候连道具的子类名都不知道，只传一个 `"Blood"` 或者 `"Bomb"`。工厂内部是个 switch 分支，负责把字符串映射到具体类的构造。外界完全不需要关心道具构造的细节。

说实话，这不是"纯正"的简单工厂——因为它只有一个静态方法而没有实例化工厂对象。但它的职责非常明确：集中管理道具创建，隔离调用方与产品类。如果以后加新道具，只需要在 PropFactory 里加一个 case，再加一个新的 prop 子类就行了，敌机的 `dropProps()` 方法完全不用动。

**2. 设计模式结构图**

```
@startuml

    + {static} createProp(type: String, x: int, y: int): AbstractProp
    __ 说明 __
    根据 type 字符串 switch 分发：
    "Blood" -> BloodProp
    "Bomb"  -> BombProp
    "Fire"  -> BulletProp
    "SuperFire" -> BulletPlusProp
    "Freeze" -> FreezeProp
}

    # locationX: int
    # locationY: int

}

    + effect(hero: HeroAircraft): int -> 瞬时加血
}

    + effect(hero: HeroAircraft): int -> 通知 Game 触发 BombUpdate
}

    + effect(hero: HeroAircraft): int -> shootNum+2 散射 2s
}

    + effect(hero: HeroAircraft): int -> shootNum*2 环射 2s

#### 2.2.3 工厂方法模式 (Factory Method Pattern)

**1. 应用场景分析**

游戏里有普通敌机、精英机、精锐机、王牌机、Boss 机，后来又加了三种特殊敌机——自爆机（Kamikaze）、闪避机（Dodge）、护盾机（Shield）。每种敌机的初始化参数差异很大：地位不同、速度不同、血量不同、默认射击策略也不同。如果让 `Game` 类直接在 `generateEnemy()` 里 `new MobEnemy(...)`、`new EliteEnemy(...)`，那 Game 就会和所有敌机具体类耦合。

工厂方法模式提供了一个清晰的接口 `EnemyFactory`，只定义一个 `createEnemy()` 方法。每种敌机对应一个工厂实现：`MobEnemyFactory`、`EliteEnemyFactory`……一直到 `BossEnemyFactory`。Game 持有所有工厂实例的引用，在需要生成敌机时按概率随机调用某个工厂。

这个设计的弹性在后期加新敌机时体现得很明显。自爆机、闪避机、护盾机是前一次实验自己加的，lab6 指导书里根本没提这些类型。但因为它们都继承自 `AbstractAircraft`，只需要各写一个工厂实现 `EnemyFactory`，然后在 Game 里注册这个工厂即可——完全不用改动任何现有敌机或工厂的代码。

#### 2.2.4 策略模式 (Strategy Pattern)

**1. 应用场景分析**

不同飞机的射击方式差别很大。普通敌机不射击，精英机单排直射，精锐机双排直射，王牌机散射，Boss 360° 环射 20 发。英雄机更复杂——默认直射，吃了火力道具变散射，吃了超级火力道具变环射，道具到期还要恢复。

如果把这些射击逻辑直接写在每个飞机子类里，代码复用几乎为零。更关键的是，英雄机的射击策略需要在运行时动态切换——它不可能用一个硬编码的方法来实现。

策略模式把射击算法从飞机类里抽出来，封装成独立的策略类：`StraightShootStrategy`（直射）、`ScatterShootStrategy`（散射）、`RingShootStrategy`（环射）、`NullShootStrategy`（不射击）。每架飞机在构造时指定默认策略，`shoot()` 方法直接委托给 `shootStrategy.Shoot(this, speedSet)`。英雄机要切换时，调 `setShootStrategy()` 就行，完全不需要改自己的类代码。

**2. 设计模式结构图**

```
@startuml
' 策略模式 — 射击系统（Strategy Pattern）
skinparam classAttributeIconSize 0

interface ShootStrategy <<Strategy>> {
    + Shoot(aircraft: AbstractAircraft, speedSet: int): List<BaseBullet>
}

class NullShootStrategy <<ConcreteStrategy>> {
    + Shoot(...): List<BaseBullet> -> 返回空列表
    用于：MobEnemy（普通敌机不射击）
}

class StraightShootStrategy <<ConcreteStrategy>> {
    + Shoot(...): List<BaseBullet> -> 沿 direction 直线飞行
    多颗子弹横向平行排列
    用于：英雄机(默认)、EliteEnemy、ElitePlusEnemy
}

class ScatterShootStrategy <<ConcreteStrategy>> {
    + Shoot(...): List<BaseBullet> -> 横向扇形分散
    横向速度随子弹序号递增
    用于：EliteProEnemy、英雄机(火力道具)
}

class RingShootStrategy <<ConcreteStrategy>> {
    + Shoot(...): List<BaseBullet> -> 360° 环形均匀发射
    角度 = (2π / shootNum) * i
    用于：BossEnemy、英雄机(超级火力道具)
}

abstract class AbstractAircraft <<Context>> {
    # shootStrategy: ShootStrategy
    # shootNum: int
    # power: int
    # direction: int
    __
    + setShootStrategy(strategy: ShootStrategy): void
    + {abstract} shoot(): List<BaseBullet>
}

class HeroAircraft {
    默认：StraightShootStrategy
    火力道具 -> ScatterShootStrategy（2s 后恢复）
    超级火力 -> RingShootStrategy（2s 后恢复）
}

class MobEnemy { 策略：NullShootStrategy }
class EliteEnemy { 策略：StraightShootStrategy, shootNum=1 }
class ElitePlusEnemy { 策略：StraightShootStrategy, shootNum=2 }
class EliteProEnemy { 策略：ScatterShootStrategy, shootNum=3 }
class BossEnemy { 策略：RingShootStrategy, shootNum=20 }

ShootStrategy <|.. ScatterShootStrategy

#### 2.2.5 数据访问对象模式 (DAO Pattern)

**1. 应用场景分析**

游戏有排行榜功能——玩家打完一局后输入名字，成绩被持久化保存，下次打开游戏还能看到历史记录。存储方式用的是 Java 对象序列化到 `data/record.dat` 文件。

这里的问题和之前一样：如果 Game、ScoreBoard 这些类直接操作文件读写，业务逻辑和文件 I/O 就搅在一起了。以后想把数据存到数据库、或者远程服务器，所有用到排行榜的地方全都得改。

DAO 模式在这里充当了"数据层"的角色。`RecordDao` 接口对外暴露三个方法：`getAllRecords(difficulty)`、`addRecord(record)`、`deleteRecordById(id)`。`RecordDaoImpl` 是具体实现，负责文件的序列化读写。上层调用方（Game 存成绩、ScoreBoard 查排行榜）只依赖接口，完全不知道底层是文件还是数据库。

模式结构参考了类似 MVC 的分层思路：`Main` 作为 CompositionRoot 在启动时创建唯一的 `RecordDaoImpl` 实例，然后注入给 Game 和 ScoreBoard。所有对排行榜的操作走同一个 DAO 实例，保证了数据一致性，也避免了多个地方各自打开文件导致的并发问题。

#### 2.2.6 观察者模式 (Observer Pattern)

**1. 应用场景分析**

炸弹和冰冻是飞机大战里两种比较特殊的道具——它们不直接给英雄机加属性，而是影响屏幕上所有的敌机和子弹。炸弹一来，普通敌机直接炸毁，精英机也跟着消失，但王牌机只是扣点血，Boss 完全不为所动。冰冻也一样：普通敌机冻住就再也动不了，精英机过几秒还能恢复，Boss 根本不吃这套。

说实话，最开始实现的时候，我差点就在道具类里写了一堆 if-else 去判断敌机类型。但这样做的坏处很明显：每加一种新敌机，道具代码就得跟着改，耦合得一塌糊涂。

观察者模式提供了一个更干净的思路。把道具当成"通知源"——炸弹爆炸或者冰冻触发的时候，由 Game 这个通知中枢去遍历所有敌机和子弹，逐个调用它们身上的回调方法 `updateOnBomb()` 或 `updateOnFreeze()`。具体怎么响应，是每个敌机自己说了算的：MobEnemy 选择直接 vanish 并返回分数，EliteProEnemy 选择扣 35 血但留一条命，BossEnemy 直接返回 0 表示免疫。冰冻也是，各敌机通过返回不同的帧数（-1 永久 / >0 定时 / 0 免疫）来声明自己的冻结行为。

这种"通知-响应"的分离让道具和敌机之间几乎零耦合，新增敌机只需要实现对应的 Observer 接口就行。

**各观察者的差异化响应如下：**

| 观察者类 | Bomb（炸弹） | Freeze（冰冻） |
|---|---|---|
| MobEnemy / Kamikaze / Dodge / Shield | 直接 vanish，返回 10 分 | 返回 -1（永久冻结） |
| EliteEnemy | vanish，返回 20 分 | 返回 100 帧（4 秒） |
| ElitePlusEnemy | vanish，返回 25 分 | 返回 75 帧（3 秒） |
| EliteProEnemy | 扣 35 HP，钳制 ≥ 1，设 bombInvincible 标记 | 返回 125 帧，速度降至 50% |
| BossEnemy | 返回 0（免疫） | 返回 0（免疫） |
| EnemyBullet | N/A（被 BombUpdate 清空列表） | 返回 125 帧，速度暂存后置零 |
| HeroAircraft / HeroBullet | 不参与 | 返回 0（不参与冰冻） |

**2. 设计模式结构图**

```
@startuml
' 观察者模式 — 炸弹与冰冻道具效果分发
skinparam classAttributeIconSize 0

    - enemyBullets: List<BaseBullet>
    - enemyFreezeTicks: IdentityHashMap<AbstractAircraft, Integer>

#### 2.2.7 模板方法模式 (Template Method Pattern)

**1. 应用场景分析**

游戏需要支持三种难度——简单、普通、困难。三种难度的主循环结构完全一样：生成敌机 → 射击 → 移动 → 碰撞检测 → 道具处理 → 重绘 → 检查游戏结束。区别只在于几个"决策点"：Boss 是否出现、Boss 出场时有没有加成、游戏推进时敌机参数要不要随时间变强。

如果为每个难度单独写一份 `action()` 方法，主循环那上百行代码就要复制三份，后面改一个步骤就得同步三处。这跟"不写重复代码"的原则完全是背道而驰的。

模板方法模式正好适合这种场景。把 `action()` 声明为 `final`，锁死主循环的十个步骤顺序，然后在需要"做决定"的地方暴露 `protected` 钩子方法——`shouldSpawnBoss()`、`onBossSpawn()`、`onProgressTick()`、`progressIntervalTicks()`。子类只需要覆盖这些钩子，不用碰主循环骨架。

`EasyGame` 把 `shouldSpawnBoss()` 覆盖成 `return false`，就自然地实现了"永不出 Boss"的效果；`HardGame` 在 `onProgressTick()` 里额外衰减 `heroShootCycle` 和 `enemyShootCycle`，交火节奏就随难度一起加速了。

**难度递进的具体参数：**

| 参数 | 普通 (NormalGame) | 困难 (HardGame) |
|---|---|---|
| enemySpawnCycle | × 0.92 | × 0.92 |
| enemySpeedMultiplier | × 1.10 | × 1.10 |
| enemyHpMultiplier | × 1.15 | × 1.15 |
| heroShootCycle | 不变 | × 0.95（射得更快） |
| enemyShootCycle | 不变 | × 0.92（敌机更凶） |
| Boss HP | 不变 | × 1.30^N（累乘提升） |
| 递进间隔 | 750 帧（30 秒） | 750 帧（30 秒） |

初始参数在 Game 构造时通过 Difficulty 枚举注入：
- **简单**：`enemySpawnCycle = 12`, `enemyShootCycle = 18`
- **普通**：`enemySpawnCycle = 8`, `enemyShootCycle = 12`
- **困难**：`enemySpawnCycle = 6`, `enemyShootCycle = 9`

模板方法的 hook 是在这个初始差异之上再加时间递进，两层机制叠加，让三种难度从第一秒就有明显差别，时间越长拉得越开。

**2. 设计模式结构图**

```

### 2.3 自主创新设计：三种特殊敌机

实验指导书要求实现五种标准敌机（普通、精英、精锐、王牌、Boss），但我觉得敌机类型还可以玩出更多花样。翻了翻其他弹幕游戏的机制，决定自己加三种特殊敌机：**闪避机**（挨打后横移躲子弹）、**自爆机**（死亡时向四周喷射弹幕）、**护盾机**（自带一层护盾血量优先承伤）。

这三个设计的出发点其实不太一样。闪避机是让"打中了"这件事变得不再确定——你以为命中了，它一个侧闪又活了。自爆机是改变"击杀"的风险评估——不是打掉就行，还得躲它死后喷出来的弹幕。护盾机是在数值层做些差异化——让一部分伤害被护盾吃掉，提供一种血厚的"错觉"。

它们不是孤立地塞进游戏里的，而是完全复用现有的架构：都继承 `AbstractAircraft`，都通过各自的 `EnemyFactory` 创建，都在 Game 的概率分布表里占据一席之地（各 10%），都被观察者模式统一管理炸弹/冰冻行为。能做到这一点，正好说明了前面那些设计模式不是摆设——架构的弹性在加新东西的时候最能看出来。

**闪避机 (DodgeEnemy)**

```
      子弹命中 → decreaseHp()
                    ↓
              存活 && 未在闪避中?
               ↙            ↘
            是               否
             ↓               ↓
   随机选左右方向         正常扣血
   横向速度 = ±15
   闪避持续 5 帧
             ↓
   forward() 每帧递减 dodgeFrames
             ↓
   dodgeFrames == 0 → 恢复原始 speedX
```

核心机制很简洁：重写了 `decreaseHp()`——在中弹后如果还活着、且当前没在闪避中，就随机挑一个方向以 15px/帧的速度横向漂移 5 帧。`forward()` 里每帧递减计数器，归零就恢复到 `originalSpeedX`。这个设计让闪避机成了一个"反应式"的敌机——它的行为不是预设好的路线，而是被玩家的射击触发的。在玩法上，它逼迫玩家不能只靠"命中"来判断威胁是否解除，需要多补一两枪确认击杀。

**自爆机 (KamikazeEnemy)**

```
   KamikazeEnemy implements Explosive
         │
   death (子弹击杀 / 撞击 / 炸弹)
         ↓
   Game.crashCheckAction() 检测到 notValid
         ↓
   if (enemyAircraft instanceof Explosive)
      enemyBullets.addAll(((Explosive) enemyAircraft).explode())
         ↓
   explode(): 8 方向 × 速度 8 × 威力 20 的弹幕
```

自爆机不射击（`NullShootStrategy`），血量低（25），向下冲得很快（12px/帧）。真正有趣的是它实现了 `Explosive` 接口——`explode()` 方法以 8 个方向（间隔 45°）向外喷射 `EnemyBullet`。Game 在检测到它死亡时通过 `instanceof Explosive` 判断，把弹幕注入到敌人子弹列表里。

这里有个设计细节值得一提。`Explosive` 是一个独立接口，不是挂在 BombObserver 或 FreezeObserver 名下的。为什么？因为自爆既不是"观察者响应道具"，也不是"被炸弹触发"——它是一种"死亡事件的回调"。语义不同，接口分开，干净利落。

另外，撞击也能触发自爆。英雄机如果撞上自爆机，双方都损毁，但自爆机在 `vanish()` 之前会先喷射弹幕。Game 在碰撞检测的两个分支（子弹击杀和飞机撞击）都加了 `instanceof Explosive` 判断，确保不管怎么死，自爆弹幕都会触发。

**护盾机 (ShieldEnemy)**

```
   BulletHit → decreaseHp(decrease)
                  ↓
            shieldHp > 0?
            ↙          ↘
          是            否
          ↓             ↓
   吸收 min(shield, decrease)  全量扣真血
   剩余 damage 继续...
          ↓
   shieldHp == 0 → 盾破（打印日志）
   切换到无盾裸机贴图
```

护盾机带一个独立的 `shieldHp = 50`。`decreaseHp()` 被重写为"先扣盾，溢出才扣真血"——这是一个优先级吸收链。视觉效果同步反馈：`getImage()` 根据护盾是否还在返回不同的贴图——有盾时是一张加了半透明蓝色光圈的合成图（用 `Graphics2D` 在构造时预渲染，避免每帧重复开销），盾破了就切换回原始敌机贴图。

炸弹对护盾机是"无视护盾直接消灭"——这个设计是故意的。如果护盾能防炸弹，那炸弹这个道具在护盾机面前就废了。让炸弹穿透护盾，保持了炸弹作为"紧急清屏手段"的可靠性。

**与前六次实验模式的融合**

这三种敌机虽然是自己加的，但在整个设计模式的框架里完全零摩擦。它们对每个已有模式的兼容情况：

| 模式 | 闪避机 (DodgeEnemy) | 自爆机 (KamikazeEnemy) | 护盾机 (ShieldEnemy) |
|---|---|---|---|
| 工厂方法 | 有独立 `DodgeEnemyFactory` | 有独立 `KamikazeEnemyFactory` | 有独立 `ShieldEnemyFactory` |
| 策略模式 | `StraightShootStrategy` | `NullShootStrategy`（不射击） | `StraightShootStrategy` |
| 观察者(炸弹) | vanish，返回 25 分 | vanish+自爆，返回 20 分 | vanish（无视护盾），返回 35 分 |
| 观察者(冰冻) | 永久静止（-1） | 永久静止（-1） | 永久静止（-1） |
| 模板方法 | 受 `enemyHpMultiplier` / `enemySpeedMultiplier` 影响 | 同左 | 同左 |
| 道具掉落 | 血/火/超火（各 10%） | 不掉落（自爆机无掉落） | 血/火/超火/冰冻（略高概率） |

这里最让我满意的是，炸弹对护盾机"无视护盾"的处理只需要在 `updateOnBomb()` 里直接 `vanish()` 就行——因为 `updateOnBomb()` 走的是观察者模式的路径，它不经过 `decreaseHp()`，自然就绕过了护盾吸收逻辑。不需要额外判断，设计模式本身的路径就已经分开了。

如果以后要加新特性——比如冰冻道具的视觉特效、或者一种"EMP机"（定期干扰英雄机鼠标控制）——模型已经很清晰了：新建敌机类继承 `AbstractAircraft`，建对应工厂，在 Game 的概率表里加一行，在观察者方法里定义炸弹/冰冻/EMP 的响应。三个步骤，不碰一处已有代码。

## 3. 收获和反思

这次实验是把整个学期的设计模式串起来做了一次实战，回过头来看，有几个感受比较深的地方。

**模式不是孤立的。** 一开始每个实验单独做一个模式，感觉都懂。但真正把七个模式放在同一个项目里，才意识到它们之间是有交叉的。比如英雄机——单例模式管理它的实例唯一性，策略模式管理它的射击方式，观察者模式让它响应炸弹/冰冻。一个类同时参与三种模式，但职责边界很清楚。这说明设计模式的粒度不是在"类"这一层，而是在"职责"这一层。

**模板方法 + 钩子的设计，比想象中好用。** 把 `action()` 锁成 `final` 之后，主循环的任何一个步骤都不可能被意外重写。这其实是一种保护——不是保护代码不被改，而是保护"调用顺序"这个最重要的架构决策不被破坏。三个子类加起来不到 100 行，但三种难度的手感差别非常大，说明把可变部分浓缩成几个钩子就够了。

**观察者模式用 IdentityHashMap 做定时器的做法，其实有点"非典型"。** 标准的观察者模式讲的是 attach/detach/notify，但这个项目里没有显式的订阅过程——Game 直接在道具触发时遍历它已有的列表，谁实现了接口谁就响应。冻结倒计时是按对象存的，不是全局的一个 counter。这种"变体"反而更贴合实际需求：标准模式给出的是一套思路，具体怎么落地是要看场景的。

**加新敌机比想象中轻松，前提是模式选对了。** lab6 只规定了五种标准敌机的观察者行为，但那三种自己加的特殊敌机（自爆机、闪避机、护盾机）归到 Mob 类只需改两行——炸弹行为继承 Mob 的 vanish，冰冻返回 -1。要是当初没用观察者模式而是在道具里写类型判断，这三架新飞机就会成为麻烦。

**PlantUML 的文本驱动方式比拖拽画图更适合程序员。** UML 图和代码放在同一个仓库里，改代码的同时顺手改 `.puml` 文件，diff 里能直接看到 UML 的变化。这在拖拽式的 UML 工具里是很难做到的。
